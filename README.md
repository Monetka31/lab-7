# Лабораторная работа №7. Проектирование REST API

**Тема:** Система бронирования рабочих мест (мой вариант из лабораторной №1)

## Что я сделала

Взяла сайт из лабораторной №6 и научила сервер отвечать не только HTML-страницами, но и данными в формате JSON. Теперь у системы есть API: через него другая программа (например, клиентское приложение из лабораторной №5) может получать, добавлять, менять и удалять данные.

Ресурсов три: **бронирования**, **рабочие места** и **сотрудники**. Для каждого сделаны все пять операций: список, одна запись, создание, изменение и удаление. Данные пока лежат в JSON-файлах в папке `storage/`, без базы данных.

Сайт из лабораторной №6 остался и работает как раньше. Единственное отличие: в бронировании теперь хранится не ФИО в виде текста, а номер сотрудника (`employee_id`) — так бронирование связано с отдельным ресурсом «сотрудники».

## Шаг 1. Ресурсы

| Ресурс | URL | Методы | Для чего | Формат данных |
|---|---|---|---|---|
| Бронирования | `/api/bookings`, `/api/bookings/{id}` | GET, POST, PUT, PATCH, DELETE | записи о том, кто и когда занял рабочее место | JSON |
| Рабочие места | `/api/workspaces`, `/api/workspaces/{id}`, `/api/workspaces/{id}/bookings` | GET, POST, PUT, PATCH, DELETE | столы и переговорные, где они находятся и чем оборудованы | JSON |
| Сотрудники | `/api/employees`, `/api/employees/{id}`, `/api/employees/{id}/bookings` | GET, POST, PUT, PATCH, DELETE | люди, которые бронируют места | JSON |

Адреса — существительные во множественном числе, действие определяет HTTP-метод, а не слово в адресе. Все адреса API начинаются с `/api`, чтобы не путать их со страницами сайта.

## Шаг 2. Мой перенос с примера «задачи / проекты»

| Что нужно было определить | Что получилось |
|---|---|
| Основная сущность | бронирование (`bookings`) |
| Связанная сущность | рабочее место (`workspaces`) |
| Третья сущность (вместо участников) | сотрудник (`employees`) |
| Поля бронирования | id, workspace_id, employee_id, status, time_slot, booking_date |
| Поля рабочего места | id, title, location, description |
| Поля сотрудника | id, name, email, department |
| Допустимые значения | status: `new`, `confirmed`, `cancelled`; time_slot: `morning`, `afternoon`, `full_day`; department: `it`, `sales`, `hr`, `finance` |

Что я поменяла по сравнению с примером:

- `TaskApiController` стал `BookingApiController`, `ProjectApiController` — `WorkspaceApiController`, `UserApiController` — `EmployeeApiController`; модели переименованы так же.
- В каждой модели поменяла имя файла с данными (`bookings`, `workspaces`, `employees`) и написала свои данные в `storage/`.
- Переписала проверку полей (`validate()`) и отбор нужных полей (`clean()`) под свои поля.
- Зарегистрировала свои маршруты в `routes/web.php`. Старые адреса из примера (`/api/tasks`, `/api/projects`, `/api/users`) теперь отвечают 404.
- Маршрутизатор, `helpers.php` и `JsonRepository` почти не трогала, только поправила комментарии.

Две вещи добавила от себя, потому что они подходят к моей теме:

1. **Проверка занятости.** Одно место нельзя забронировать на ту же дату и в то же время: если пытаться, сервер отвечает 409. Время пересекается, если оно одинаковое или одно из бронирований на весь день. Отменённые бронирования не мешают.
2. **Защита от удаления нужных записей.** Рабочее место или сотрудника, на которых есть бронирования, удалить нельзя (409), иначе в бронированиях остались бы номера несуществующих записей. Это как с проектом, в котором есть задачи, в примере.

## Обзор API

Полное описание каждой точки — в [`docs/api.md`](docs/api.md).

| Метод | URL | Что делает | Код при успехе |
|---|---|---|---|
| GET | `/api/bookings` | список бронирований (фильтры `status`, `workspace_id`, `employee_id`, `date`) | 200 |
| GET | `/api/bookings/{id}` | одно бронирование | 200 |
| POST | `/api/bookings` | создать бронирование | 201 |
| PUT, PATCH | `/api/bookings/{id}` | изменить бронирование | 200 |
| DELETE | `/api/bookings/{id}` | удалить бронирование | 204 |
| GET | `/api/workspaces` | список рабочих мест | 200 |
| GET | `/api/workspaces/{id}` | одно рабочее место | 200 |
| GET | `/api/workspaces/{id}/bookings` | бронирования рабочего места | 200 |
| POST | `/api/workspaces` | создать рабочее место | 201 |
| PUT, PATCH | `/api/workspaces/{id}` | изменить рабочее место | 200 |
| DELETE | `/api/workspaces/{id}` | удалить рабочее место | 204 |
| GET | `/api/employees` | список сотрудников (фильтр `department`) | 200 |
| GET | `/api/employees/{id}` | один сотрудник | 200 |
| GET | `/api/employees/{id}/bookings` | бронирования сотрудника | 200 |
| POST | `/api/employees` | создать сотрудника | 201 |
| PUT, PATCH | `/api/employees/{id}` | изменить сотрудника | 200 |
| DELETE | `/api/employees/{id}` | удалить сотрудника | 204 |

Всего 17 точек, у каждого ресурса есть все пять операций.

### Примеры (на бронированиях)

**Список с фильтром** — `GET /api/bookings?status=confirmed`, ответ 200: массив из трёх подтверждённых бронирований.

**Одна запись** — `GET /api/bookings/3`, ответ 200:

```json
{
  "id": 3,
  "workspace_id": 1,
  "employee_id": 3,
  "status": "cancelled",
  "time_slot": "full_day",
  "booking_date": "2026-10-15"
}
```

**Создание** — `POST /api/bookings`

```json
{ "workspace_id": 4, "employee_id": 2, "booking_date": "2026-11-02" }
```

Ответ 201, в заголовке `Location: /api/bookings/8`:

```json
{
  "id": 8,
  "workspace_id": 4,
  "employee_id": 2,
  "status": "new",
  "time_slot": "full_day",
  "booking_date": "2026-11-02"
}
```

Поля `status` и `time_slot` я не присылала — сервер подставил значения по умолчанию (`new` и `full_day`).

**Изменение** — `PATCH /api/bookings/8` с телом `{ "status": "confirmed" }`, ответ 200: вернулось бронирование, у которого поменялся только статус.

**Удаление** — `DELETE /api/bookings/8`, ответ 204 без тела. Повторный такой же запрос даст 404.

### Ошибки

| Код | Пример | Что значит |
|---|---|---|
| 400 | в теле запроса не JSON (одинарные кавычки) | сервер не смог прочитать тело |
| 404 | `GET /api/bookings/999`, `GET /api/tasks` | записи или адреса нет |
| 405 | `DELETE /api/bookings` | у адреса нет такого метода, в заголовке `Allow` список разрешённых |
| 409 | бронь на занятое место; удаление места с бронированиями | запрос понятный, но противоречит данным |
| 422 | несуществующее место, дата `2026-13-45` | данные не прошли проверку, в ответе список ошибок по полям |
